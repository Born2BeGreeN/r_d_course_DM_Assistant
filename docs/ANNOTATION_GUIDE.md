# Правила анотації AdventureCard

Це узгоджені рішення реалізації HW1, а не додаткові вимоги курсу. Контракт — [src/schema.py](../src/schema.py), його експорт для обох майбутніх адаптерів — [adventure_card.schema.json](adventure_card.schema.json). Ручні golden-відповіді заповнює та перевіряє користувач; цей крок їх не створює.

Покрокове копіювання шаблонів, збереження JSON, ручний reviewed stamp і completion gate описано в [MANUAL_ANNOTATION.md](MANUAL_ANNOTATION.md). Індекс джерел — [data/golden_templates/INDEX.md](../data/golden_templates/INDEX.md).

## Єдине джерело фактів

Анотуйте лише фіналізований UTF-8 вхід із вибраного hash-locked snapshot. Поточний pointer — `data/active_dataset.json`; обидва адаптери мають отримувати ті самі записи через `src.dataset.load_snapshot`. Фрагмент представляє тільки свої сторінки й segments, а не весь PDF чи серію пригод.

Не беріть факти з filename, PDF metadata, інших пригод, пропущених розділів, пам'яті про Forgotten Realms або правил D&D. Оригінальний PDF допомагає виявити проблему підготовки, але не є додатковим невидимим моделям джерелом відповіді. Якщо читабельний на зображенні факт відсутній у finalized OCR/text layer, його не включають до картки. Питання записують окремо; виправлення джерела потребує нової ревізії входу та перевірки сумісності labels/results.

Зберігайте оригінальні імена, регістр і мову джерела. Італійські чи іспанські факти не перекладайте англійською або українською. Пишіть короткі буквальні source phrases, а не переказ. Допустима лише механічна нормалізація: Unicode NFC, прибирання крайніх пробілів, заміна послідовностей whitespace одним пробілом. Маркери `[PDF_PAGE=N]` і номери сторінок не є фактами картки. Не відновлюйте невідомі літери або зміст із пошкоджених гліфів. Для імені/назви з дефектом використовуйте інше чітке входження в тому самому вході, якщо тотожність безсумнівна; інакше залишайте питання зовні картки.

## Обов'язкові ключі

Картка завжди містить рівно вісім ключів. `NPC` завжди містить рівно `name` і `role`. Зайві поля заборонено на обох рівнях.

| Поле | Правило |
|---|---|
| `title` | Явна назва цієї пригоди, перше чітке входження. Заголовок секції на кшталт «Introduction» не замінює назву пригоди. Коли назви немає — `null`. |
| `language` | Одне з `en`, `uk`, `mixed`, `other`, `unknown` за правилами нижче. Це мова вхідного тексту, не мови персонажів у stat blocks. |
| `recommended_level` | Найкоротша достатня буквальна фраза з явно рекомендованим рівнем персонажів саме для цієї пригоди/сцени. Зберігайте range та умову застосування. Якщо прямої рекомендації немає — `null`. |
| `hook` | Одне завершене source sentence з безпосередньою зав'язкою, проблемою чи метою; до 40 whitespace-слів після механічної нормалізації. Береться перше придатне речення в порядку входу. Якщо такого немає — `null`. |
| `npcs` | Об'єкти тільки для явно названих, сюжетно релевантних NPC. `name` — рядок; `role` — коротка перша чітка source phrase про роль або `null`. Якщо немає підтриманих NPC — `[]`. |
| `locations` | Короткі наявні в тексті назви/фрази для місць дії, цілей подорожі та доступних сцен/кімнат. Proper name не обов'язкове: явно описаний Guest room може бути локацією. За відсутності — `[]`. |
| `threats` | Короткі source phrases для явних небезпек поточного сюжету: ворожі актори, пастки, небезпечні умови. Зберігайте суттєві умови. За відсутності — `[]`. |
| `rewards` | Явні обіцяні/отримувані переваги та доступна для знаходження/збирання здобич; короткі source phrases зі stated quantities і необхідними умовами. За відсутності — `[]`. |

40 слів для `hook` — локальне рішення, що робить «коротке речення» перевірюваним під час ручного review. Не склеюйте речення, не обрізайте довге речення й не складайте новий summary. Речення може бути в synopsis або prose, а не лише під заголовком Hook. Не беріть рекламний вступ, цитату без зав'язки або історичну довідку замість реального початку проблеми. Скорочення в іменах не вважайте окремими реченнями.

Рівень: не підміняйте рекомендацію NPC/class/spell level, CR, віком, номером редакції чи «рівнем виснаження». Не розраховуйте party level за монстрами. Посилання на іншу пригоду/атракціон не переносить його level на поточну. Якщо source прямо пропонує кілька режимів/рівнів, беріть першу явну рекомендацію разом з її умовою; конфлікт позначайте в окремих notes, а не створюйте неіснуючий спільний range.

## Named NPC та тотожність

- NPC — не тільки гуманоїд: названий грифон, тварина чи інша істота підходить, якщо текст надає їй сюжетну роль. Не вигадуйте ім'я анонімній групі, професії чи monster type.
- Включайте явно релевантних закадрових акторів, наприклад замовника або антагоніста, чиї дії рухають наданий сюжет. Персонаж не мусить особисто з'являтися на сцені.
- Не включайте authors/playtesters, явно названих player characters, божеств як декоративні символи, історичних героїв у підписі картини чи імена тільки як зовнішні посилання. Якщо такому персонажу прямо надано поточну сюжетну дію/роль, оцінюйте її за цим контекстом, а не за популярністю імені.
- Одна сутність — один NPC. Для неї обирайте перше чітке повне ім'я, а не автоматично першу коротку згадку. Пізніше повне ім'я може замінити ранню коротку форму; порядок списку все одно визначає перша згадка сутності.
- Об'єднуйте aliases/варіанти лише за явним alias або однозначною кореференцією в самому вході. Схожості літер недостатньо. При різних spellings без упевненості не вигадуйте «правильне» написання та не ототожнюйте різних осіб. Якщо співвіднесення не вирішується, зафіксуйте питання до frozen annotation поза карткою.
- `role` — перша чітка коротка фраза про цю особу, не вигаданий переклад чи набір усіх її характеристик. Якщо роль не названа, ключ залишається з `null`.

## Дедуплікація та порядок

Для всіх списків використовуйте порядок першої згадки сутності/факту. Ідентичні фрази після дозволеної whitespace/NFC-нормалізації та очевидні повтори того самого заголовка дають один елемент. Регістр не змінюйте механічно. Для alias використовуйте правила NPC; не зливайте різні кімнати лише через однаковий generic label без доказу, що це те саме місце.

Для повторного threat/reward з різними деталями беріть першу достатню фразу, не складайте нове речення з віддалених уривків. Різні явно stated умови чи нагороди можуть бути різними елементами. Не повторюйте всі значення одного списку в іншому: NPC може також бути threat, тільки якщо небезпеку прямо підтверджено; його ім'я саме по собі не робить його загрозою.

Стартове спорядження, товари з ціною, декорації та довідковий список предметів не є автоматичними rewards. Явно discoverable loot, обіцяна платня, приз конкурсу чи зароблена привілея підходять. Умовну нагороду не подавайте як гарантовану; не переводьте валюту, не обчислюйте сумарну вартість і не додавайте XP з правил.

## Класифікація мови

- `en`: змістовна оповідь англійською; `uk`: українською.
- `other`: одна інша визначувана природна мова, зокрема італійська чи іспанська. Поля при цьому залишаються мовою джерела.
- `mixed`: є змістовні сюжетні уривки двома або більше природними мовами — щонайменше по одному завершеному реченню або самостійному інформативному bullet/clause кожною. Це може бути не тільки пара англійська/українська.
- Власні імена Waterdeep, D&D terms, окремі запозичення, назви фільмів/книг, логотипи, credits і legal boilerplate самі по собі не створюють `mixed`. Ігноруйте повторені колонтитули для визначення мови.
- `unknown`: недостатньо читабельного природного тексту для впевненого рішення, наприклад залишилися лише імена чи пошкоджені гліфи. Порожній результат не позначайте довільно як `en`; `null` для language не дозволено.

## Пропущені факти та межі валідації

Відсутній scalar — `null`, відсутня колекція — `[]`, відсутня роль названого NPC — `role: null`. Ключі не пропускайте. Не використовуйте `"unknown"`, `"N/A"` або порожній рядок замість відсутнього факту (виняток — спеціальне enum-значення `language: "unknown"`). Не створюйте порожнього NPC як заповнювач.

Pydantic перевіряє типи, required keys і відсутність extra properties; він не доводить відповідність джерелу, правильність aliases, мови чи семантичного рішення. Правило 40 слів, source wording і відсутність hallucinations також потребують review. Структурно валідний JSON ще не означає правильну екстракцію.

`text_id`, `document_id`, PDF pages, hashes, provenance, annotation status, evidence notes, model/prompt/sampling, tokens, latency, cost, retry/repair та OCR diagnostics живуть **поза карткою**. Не додавайте для них дев'ятий ключ і не ховайте їх у `role` чи інших рядках.

## Неоднозначності фактичних development-входів

Це пояснення рішень, не готові labels або повні картки.

| Development-джерело | Спостереження та правило |
|---|---|
| Una Notte da Grifoni, PDF p.2–8 | Італійська оповідь містить англомовні proper names і D&D terms; це не робить її автоматично `mixed`. Фраза про рекомендований character level відрізняється від «1 livello di indebolimento». Borasco — названий грифон; remote antagonist може бути релевантним, навіть коли прямо сказано, що він не з'являється на сцені. Інформацію тільки з пропущених актів не додаємо. |
| Witchlight Beer Festival, PDF p.1–7 | `1st level characters` граматично стосується згаданої Mystery Mine, а не однозначної рекомендації рівня для всього фестивалю. Переносити його без прямого зв'язку не можна. Товари по 1–500 gold pieces не є нагородами лише через ціну. Для `hook` шукаємо перший прямий сюжетний trigger, а не рекламний вступ про інтеграцію в будь-яку campaign. |
| Adventures Daycare, PDF p.1–11 | Вік дітей `4-5`, класи/рівні Ordark і spellcaster level у stat block не визначають рекомендований party level. Стартові toy/legendary items не є автоматичними rewards. Є spellings Ordark/Ordurk і Talaryl/Taraly: об'єднання можливе за однозначною локальною кореференцією, не fuzzy spelling і не зовнішніми знаннями. Yondalla як символ на armor та історичні згадки в картинах самі по собі не є active NPC. Повторені OCR-заголовки не означають багато різних локацій або назв. |

Поки schema/annotation rules не заморожені, unresolved entity questions записують окремо для узгодження. Не змінюйте golden labels після порівняння моделей, щоб покращити метрики. Точний evaluator та workflow ручного review належать до наступних кроків.
